# داشبورد مالک آسان‌دسک

پنل مدیریتی [آسان‌دسک](https://github.com/hamid-hra/asandesk) با **Next.js** (فرانت‌اند) و **Django** (بک‌اند)، کاملاً داکرایز.

| تب | وضعیت |
|---|---|
| سرور و منابع | ✅ منابع واقعی همین سرور (CPU، RAM، دیسک، پهنای باند، اتصال‌های TCP) + شمار درخواست‌های اتصال (موفق، ناموفق، لغو شده) + هشدارها |
| نسخه‌ها | ✅ انتشار نسخه با فایل نصب، تاریخچه، `latest.json` برای به‌روزرسانی خودکار، نصب‌های تازه، شمار دستگاه روی هر نسخه، توزیع نسخه‌ها بین کلاینت‌ها (با راهنمای رنگی) |
| کلاینت‌ها | ✅ دستگاه‌هایی که به API پنل گزارش می‌دهند: وضعیت آنلاین، حساب، مدت اتصال، نشست‌ها، مسدودسازی، خروج اجباری؛ فیلتر و مرتب‌سازی با کلیک روی سرستون هر ستون؛ نمای «نمودارها»: روند نصب، سهم نسخه‌ها، ویندوز در برابر لینوکس و درصد کلاینت‌های به‌روز |
| بازخوردها | ✅ «ارسال بازخورد» از داخل اپلیکیشن (مشکل، پیشنهاد، سایر) همراه لاگ برنامه و تصویر، دانلود لاگ، «جدید / بررسی‌شده». تیکت نیست: به کاربر پاسخی داده نمی‌شود و اگر شماره گذاشته باشد، با او تماس می‌گیرید |
| سرورهای HA | ✅ سلامت سرورهای شناسه و رله، failover و افزودن سرور (قبلاً در تنظیمات بود) |
| تنظیمات | ✅ کاربران و دسترسی هر بخش، پشتیبان‌گیری/بازگردانی با لاگ زنده، لاگ فعالیت‌ها، لاگ داکر و به‌روزرسانی خود پنل |
| تبلیغات | 🕓 «به‌زودی» (فاز ۳) |

## راه‌اندازی روی سرور

```bash
git clone -b main https://github.com/hamid-hra/asandesk-dashboard.git
cd asandesk-dashboard
cp .env.example .env      # فقط POSTGRES_USER و POSTGRES_PASSWORD
nano .env                 # رمز دیتابیس را عوض کنید
docker compose up -d --build
```

**اولین ورود (ساخت حساب مالک):**

1. پنل را باز کنید: `http://<IP-سرور>:8080`. چون هنوز کاربری وجود ندارد، صفحهٔ «راه‌اندازی اولیه» نمایش داده می‌شود.
2. کد راه‌اندازی یک‌بارمصرف را از لاگ backend بردارید:
   ```bash
   docker compose logs backend | grep "SETUP CODE"
   # یا: docker compose exec backend python manage.py setup_code
   ```
3. کد را وارد کنید و نام کاربری و رمز عبور مالک را خودتان تعیین کنید.

بعد از ساخت حساب مالک، کد باطل می‌شود و این صفحه دیگر نمایش داده نمی‌شود. کد برای این است که اگر کسی زودتر از شما پنل را باز کرد، نتواند مالک شود.

**رازهای خودکار:** کلید Django و توکن agent در اولین اجرا به‌صورت تصادفی ساخته می‌شوند و در volumeهای `secrets` و `agent-token` می‌مانند. هیچ رازی جز رمز دیتابیس در `.env` نیست.

حدود ۳۰ ثانیه بعد از بالا آمدن، اولین داده‌های منابع سرور نمایش داده می‌شود.

### بیلد از پشت پروکسی

اگر سرور مستقیم به npm و PyPI دسترسی ندارد (خطای `ETIMEDOUT` در `npm ci` یا `pip install`)، آدرس پروکسی HTTP سرور را به بیلد بدهید:

```bash
BUILD_PROXY=http://127.0.0.1:10809 docker compose up -d --build
```

یا همین مقدار را به‌صورت یک خط `BUILD_PROXY=...` در `.env` بگذارید.

- **پروکسی باید HTTP باشد.** npm از SOCKS پشتیبانی نمی‌کند. در v2ray/xray پورت HTTP inbound را بدهید (معمولاً `10809`)، نه SOCKS (`10808`).
- **پروکسی روی همان سرور:** بیلد با شبکهٔ میزبان اجرا می‌شود، پس پروکسی روی `127.0.0.1` سرور در دسترس است.
- **قطعی وسط دانلود:** پکیج‌های دانلودشده در cache داکر می‌مانند و با اجرای دوبارهٔ همان دستور، بیلد ادامه پیدا می‌کند.
- **pull کند ایمیج‌ها:** اگر دانلود ایمیج‌های پایه از Docker Hub (python، node، postgres، nginx) هم کند بود، پروکسی خود daemon داکر را تنظیم کنید:
  ```bash
  sudo mkdir -p /etc/systemd/system/docker.service.d
  printf '[Service]\nEnvironment="HTTPS_PROXY=http://127.0.0.1:10809"\nEnvironment="NO_PROXY=localhost,127.0.0.1"\n' \
    | sudo tee /etc/systemd/system/docker.service.d/http-proxy.conf
  sudo systemctl daemon-reload && sudo systemctl restart docker
  ```
- **زمان اجرا:** کانتینرها بعد از بیلد به اینترنت نیاز ندارند.

### تنظیمات اختیاری

این مقادیر پیش‌فرض دارند. فقط در صورت نیاز آن‌ها را به `.env` اضافه کنید:

| متغیر | پیش‌فرض | توضیح |
|---|---|---|
| `HTTP_PORT` | `8080` | پورت پنل روی سرور (مثلاً `80`) |
| `BUILD_PROXY` | خالی | پروکسی HTTP برای دانلود پکیج‌ها هنگام بیلد (بخش بالا) |
| `PUBLIC_BASE_URL` | آدرسی که پنل با آن باز شده | دامنهٔ لینک‌های دانلود در `latest.json`، مثلاً `https://api.asandesk.ir` (کلاینت‌ها فقط این دامنه را می‌شناسند) |
| `SECURE_COOKIES` | `0` | وقتی پنل پشت HTTPS است، `1` بگذارید |
| `PANEL_KEY` | خالی (بدون قفل) | آدرس مخفی پنل؛ بخش «آدرس مخفی پنل» |
| `GIT_PROXY` | خالی (همان `BUILD_PROXY`) | پروکسی HTTP برای گرفتن نسخهٔ جدید پنل از GitHub در «به‌روزرسانی پنل» |
| `ACTIVITY_KEEP_DAYS` | `180` | ردیف‌های لاگ فعالیت بعد از این تعداد روز پاک می‌شوند (`0` = هرگز) |
| `AGENT_PORTS` | خالی (همه اتصال‌ها) | فقط اتصال‌های این پورت‌ها شمرده شود، مثلاً `21116,21117` |
| `AGENT_NET_CAPACITY_MBPS` | تشخیص خودکار یا ۱۰۰۰ | ظرفیت لینک شبکه |
| `AGENT_IP` | خالی | IP نمایش‌داده‌شده برای این سرور |
| `RELEASE_MAX_FILE_MB` | `500` | حداکثر حجم هر فایل نصب |
| `CLIENT_OFFLINE_AFTER_SECONDS` | `60` | کلاینت بعد از این مدت بدون heartbeat «آفلاین» است |
| `CLIENT_FEEDBACK_PER_HOUR` | `5` | حداکثر بازخورد هر دستگاه در ساعت |
| `FEEDBACK_MAX_LOG_MB` | `10` | سقف حجم لاگِ بازشده‌ای که همراه یک بازخورد ذخیره می‌شود |
| `RELEASE_LINK_DOMAIN` | `asandesk.ir` | لینک دانلود نسخه فقط روی این دامنه و زیردامنه‌هایش پذیرفته می‌شود |
| `RELEASE_LINK_TOTAL_TIMEOUT` | `540` | حداکثر ثانیه برای دانلود هر فایل از لینک |
| `RELEASE_LINK_ALLOW_PRIVATE` | `0` | `1` یعنی لینکی که به آدرس خصوصی برسد هم دانلود شود (فقط برای آزمایش) |

> برای ریست کامل (حذف دیتابیس، فایل‌ها و حساب مالک): `docker compose down -v`

### حالت توسعه (hot-reload)

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build
```

کد `backend/` و `frontend/` داخل کانتینرها mount می‌شود و تغییرات فوراً اعمال می‌شود.

بدون داکر (برای فرانت‌اند): Django را روی پورت 8000 اجرا کنید و بعد
`cd frontend && BACKEND_URL=http://localhost:8000 npm run dev` (پنل روی پورت 3000).

## معماری

```
                 ┌──────────── nginx :8080 ────────────┐
 مرورگر  ───────►│ /           → frontend (Next.js)     │
                 │ /api, /admin → backend (Django)      │
                 │ /releases/latest.json → volume       │
                 └──────────────────────────────────────┘
 agent (pid: host) ──► backend /api/agent/ingest  ──► PostgreSQL
```

- **backend/**: Django 5 + DRF. اپ‌ها:
  - `accounts` کاربر و نقش‌ها
  - `monitoring` دریافت داده از agent، سری‌های زمانی و هشدارها
  - `releases` نسخه‌ها و فایل‌های نصب
  - `clients` کلاینت‌ها، حساب‌های اپلیکیشن، نشست‌ها و بازخوردها، به‌علاوه API سازگار با RustDesk برای خود اپلیکیشن
  - `activity` لاگ فعالیت کاربران پنل
  - `ops` ارتباط backend با سرویس `control` (به‌روزرسانی پنل و لاگ داکر)
- **frontend/**: Next.js 16 (App Router)، RTL و فارسی. تم لایت/دارک مطابق طرح است و نمودارها SVG سفارشی هستند.
- **agent/**: اسکریپت Python (psutil) که هر ۱۵ ثانیه منابع میزبان را گزارش می‌دهد. با `pid: host` شبکه و اتصال‌های میزبان را از `/proc/1/net` می‌خواند و دیسک را از `/hostfs`.
- **control/**: سرویس کوچک Python که تنها بخش در تماس با داکر است: لاگ کانتینرها و «به‌روزرسانی پنل». روی هیچ پورتی منتشر نمی‌شود (بخش «به‌روزرسانی پنل»).
- **nginx/**: فایل‌های نصب فقط از مسیر `/api/releases/<version>/download/<platform>` و با `X-Accel-Redirect` سرو می‌شوند تا دانلودها شمرده شوند.

## نقش‌ها

| نقش | دسترسی |
|---|---|
| مالک (owner) | همه چیز: کاربران، پشتیبان‌گیری، لاگ فعالیت، به‌روزرسانی پنل و لاگ داکر (در «تنظیمات») و سرورهای HA (منوی اصلی) |
| مدیر (admin) | ویرایش سرور، نسخه‌ها، کلاینت‌ها (با نمودارها) و بازخوردها. بدون کاربران، پشتیبان‌گیری، HA، لاگ فعالیت و سیستم؛ فقط «لاگ فعالیت» را مالک می‌تواند به یک مدیر جداگانه بدهد |
| ناظر (viewer) | فقط مشاهدهٔ سرور، نسخه‌ها، کلاینت‌ها (با نمودارها) و بازخوردها. بدون پشتیبان‌گیری، HA و کاربران |
| سفارشی (custom) | دسترسی هر بخش جدا: «بدون دسترسی»، «مشاهده» یا «ویرایش» |

بخش‌های حساس برای مدیر و ناظر بسته است: **یک پشتیبان یعنی کپی کل دیتابیس**. حتی با نقش سفارشی، «مشاهدهٔ» پشتیبان‌گیری فقط فهرست را نشان می‌دهد و دانلود، ساخت و بازگردانی «ویرایش» می‌خواهد. همهٔ کاربران، با هر نقش، در «تنظیمات ← حساب من» رمز و کدهای بازیابی خودشان را مدیریت می‌کنند.

حساب مالک در اولین ورود ساخته می‌شود (بخش بالا). کاربران بعدی را مالک از «تنظیمات ← کاربران» می‌سازد. فقط نقش مالک به پنل `/admin` (Django) دسترسی دارد و نیازی هم به آن نیست.

### مرا به خاطر بسپار و فراموشی رمز

- **مرا به خاطر بسپار:** در صفحهٔ ورود، با تیک خورده ورود تا ۳۰ روز در همان مرورگر می‌ماند و بدون آن با بستن مرورگر خارج می‌شوید. فیلدهای فرم برای ذخیرهٔ رمز در مرورگر و مدیر رمز آماده‌اند؛ خود پنل رمز را جایی نگه نمی‌دارد.
- **کدهای بازیابی (بدون ایمیل):** بعد از ورود، از «تنظیمات ← حساب من ← ساخت کدهای تازه» ۱۰ کد یک‌بارمصرف بسازید و جای امن نگه دارید (کپی یا دانلود فایل متنی). کدها فقط همان لحظه نمایش داده می‌شوند و در دیتابیس فقط HMAC آن‌ها هست. تا وقتی کد ندارید، کنار نام شما نقطهٔ قرمز دیده می‌شود.
- **اگر رمز را فراموش کردید:** در صفحهٔ ورود «رمز عبور را فراموش کرده‌ام» را بزنید، نام کاربری و یکی از کدها را بدهید و رمز تازه بگذارید. بعدش ورودهای قبلی همان حساب بسته می‌شوند. تعداد تلاش‌ها محدود است (۵ بار در دقیقه).
- **کاربران دیگر:** اگر کدی ندارند، مالک از تنظیمات ← کاربران ← «تغییر رمز» رمزشان را عوض می‌کند.
- **اگر کد هم ندارید (مالک):** `docker compose exec backend python manage.py changepassword <username>`

## نسخهٔ پنل و تاریخچهٔ تغییرات

نسخهٔ پنل پایین منوی کناری نمایش داده می‌شود و با کلیک روی آن تاریخچهٔ تغییرات باز می‌شود. منبع هر دو یک فایل است: `backend/config/version.py`.

برای انتشار نسخهٔ تازهٔ پنل، یک مورد **بالای** لیست `CHANGELOG` در همان فایل اضافه کنید (نسخه، تاریخ `YYYY-MM-DD`، عنوان و موارد با نوع `new`، `change` یا `fix`). شمارهٔ نسخه از اولین مورد برداشته می‌شود و جای دیگری لازم نیست عوض شود. بعد دوباره بیلد کنید: `docker compose up -d --build`.

## ساخت کاربر و اولین ورود

کاربری که مالک می‌سازد (تنظیمات ← کاربران ← افزودن کاربر) یا برایش «تغییر رمز» می‌زند، **رمز موقت** دارد، چون رمز را کس دیگری انتخاب کرده است:

1. کاربر وارد می‌شود و پنل فقط صفحهٔ «رمز عبور خودتان را بگذارید» را نشان می‌دهد (رمز موقت، رمز تازه، تکرار). تا این کار انجام نشود سرور هم به هیچ بخش دیگری جواب نمی‌دهد (۴۰۳)، پس دور زدنش از بیرون صفحه ممکن نیست.
2. بعد از ذخیرهٔ رمز، **کدهای بازیابی** یک بار نشان داده می‌شوند (کپی یا دانلود فایل متنی) و با «کدها را ذخیره کردم» وارد پنل می‌شود.
3. رمز عوض‌کردن خودِ کاربر، یا رمزی که با کد بازیابی می‌گذارد، دیگر موقت حساب نمی‌شود. در فهرست کاربران کنار هر کسی که هنوز رمز خودش را نگذاشته برچسب «رمز موقت» هست.

**فایل ورود:** در فرم افزودن کاربر (و فرم «تغییر رمز» برای کاربر دیگر) دکمهٔ «ذخیره و دانلود فایل ورود» کاربر را می‌سازد و یک فایل متنی می‌دهد که داخلش آدرس پنل، نام کاربری و رمز موقت است. اگر `PANEL_KEY` روشن باشد، آدرس همراه کلید است تا کاربر بتواند پنل را باز کند. آدرس را می‌شود قبل از دانلود عوض کرد (مثلاً اگر خودتان با IP کار می‌کنید ولی کاربر باید با دامنه وارد شود). فایل فقط در مرورگر شما ساخته می‌شود و روی سرور ذخیره نمی‌شود. آن را از راه امن بفرستید و بعد از ورود کاربر پاک کنید؛ رمز آن فایل بعد از اولین ورود دیگر کار نمی‌کند.

## آدرس مخفی پنل (مثل x-ui)

اگر کسی دامنه یا IP و پورت پنل را بداند، صفحهٔ ورود را می‌بیند و می‌تواند رمز امتحان کند. با `PANEL_KEY` می‌توانید کاری کنید که پنل برای هر کسی که «کلید» را نداند وجود نداشته باشد.

**روشن‌کردن:** یک مقدار تصادفی بسازید و در `.env` بگذارید، بعد nginx را دوباره بالا بیاورید (بقیهٔ سرویس‌ها دست نمی‌خورند):

```bash
echo "PANEL_KEY=$(head -c 18 /dev/urandom | base64 | tr '+/' '-_' | tr -d '=')" >> .env
docker compose up -d nginx
```

مقدار باید ۱۲ تا ۶۴ نویسه از حروف انگلیسی، عدد، `-` و `_` باشد (مثل `Kjo1prZX7aST10g6UA`).

**باز کردن پنل:** در هر مرورگر یک بار آدرس زیر را باز کنید:

```
https://panel.asandesk.ir/Kjo1prZX7aST10g6UA
```

nginx یک کوکی (یک سال، HttpOnly) در همان مرورگر می‌گذارد و شما را به صفحهٔ اصلی می‌برد. از آن به بعد پنل با آدرس معمولی باز می‌شود و کلید در نوار آدرس نمی‌ماند. همین کار با هر صفحه هم می‌شود، مثلاً `/Kjo1prZX7aST10g6UA/server` شما را به `/server` می‌برد. مرورگر تازه، پنجرهٔ ناشناس یا دستگاه دیگر دوباره به همان لینک نیاز دارد.

**چه چیزی بسته می‌شود:** هر درخواست پنل (از جمله `/`، `/login`، `/api/…`، `/admin/` و حتی باز کردن مستقیم `IP:پورت`) بدون آن کوکی یک ۴۰۴ ساده می‌گیرد، انگار چیزی آنجا نیست. دو چیز بسته نمی‌شود: سرور `api.asandesk.ir` که کلاینت‌های آسان‌دسک با آن حرف می‌زنند، و مسیرهای عمومی به‌روزرسانی (`/releases/latest.json` و `/api/releases/<نسخه>/download/…`).

**خاموش‌کردن:** `PANEL_KEY` را از `.env` پاک کنید و `docker compose up -d nginx` بزنید. اگر کلید را اشتباه نوشتید (مثلاً فاصله داشت)، پنل برای همه بسته می‌ماند و علتش در `docker compose logs nginx` است، تا یک اشتباه تایپی هرگز پنل را باز نگذارد. کلید را فقط در `.env` سرور نگه دارید.

**محدودیت‌ها (مهم):**

- این کار پنل را **پنهان** می‌کند، رمزگذاری نمی‌کند. وقتی اتصال CDN به سرور بدون SSL است، کلید و کوکی و رمز ورود برای هر کسی که آن مسیر را ببیند خوانا هستند. اتصال CDN ← سرور را HTTPS کنید (گواهی self-signed روی سرور و حالت «اتصال امن به مبدأ» در CDN) و `SECURE_COOKIES=1` بگذارید.
- CDN نباید صفحه‌های پنل را کش کند. پاسخ ۴۰۴ این قفل `no-store` است، ولی تنظیم کش خود CDN با شماست.
- این لایهٔ دوم است، نه جایگزین رمز قوی. رمز مالک و کدهای بازیابی همان‌قدر مهم می‌مانند. برای محکم‌تر شدن، در `nginx/default.conf` بلوک `allow/deny` را برای IP تیم فعال کنید، یا اگر CDN شما اجازه می‌دهد، فقط IPهای CDN را بپذیرید.

## لاگ فعالیت‌ها

تنظیمات ← **لاگ فعالیت‌ها**: هر کاری که هر کاربر در پنل انجام داده، با ساعت و IP؛ مثلاً ورود و خروج، **ورود ناموفق** (با نام کاربری که امتحان شده)، انتشار یا حذف نسخه، ساخت و ویرایش کاربران، تغییر وضعیت بازخوردها، مسدود کردن دستگاه، پشتیبان‌گیری و بازگردانی، تغییر سرورهای HA و شروع به‌روزرسانی پنل. دسترسی ردشده (مثلاً ناظری که می‌خواست پشتیبان بگیرد) هم با علامت «ناموفق» ثبت می‌شود.

- **چه کسی می‌بیند:** پیش‌فرض فقط **مالک**. مالک می‌تواند دیدنش را به هر مدیر یا ناظر جداگانه بدهد: تنظیمات ← کاربران ← ویرایش کاربر ← «دیدن لاگ فعالیت‌ها». برای نقش «سفارشی» همین مورد یک ردیف در ماتریس دسترسی است (فقط «بدون دسترسی» یا «مشاهده»). کسی که این دسترسی را دارد لاگ **همهٔ افراد** را می‌بیند و می‌تواند روی یک نفر فیلتر کند؛ ولی نمی‌تواند چیزی را ویرایش یا پاک کند و فقط به کسی می‌تواند این دسترسی را بدهد که خودش دارد.
- **فیلتر:** بر اساس فرد (دکمه‌های بالای صفحه یا کلیک روی نام در هر ردیف)، بخش، بازه (امروز، ۷ و ۳۰ روز)، فقط ناموفق‌ها و جست‌وجوی متن.
- **رمزها هرگز ثبت نمی‌شوند.** ثبت فقط از روی نوع درخواست و شمارهٔ نسخه/کاربر انجام می‌شود و بدنهٔ درخواست خوانده نمی‌شود.
- **نمی‌توان لاگ را از پنل پاک یا ویرایش کرد** (در `/admin` هم فقط‌خواندنی است). ردیف‌های قدیمی‌تر از `ACTIVITY_KEEP_DAYS` روز (پیش‌فرض ۱۸۰، `0` یعنی هرگز) را سرویس scheduler خودش پاک می‌کند.
- با حذف یا تغییر نام یک کاربر، تاریخچهٔ او می‌ماند (نام و نام کاربری در خود ردیف ذخیره می‌شود).
- هر endpoint تازه‌ای که اطلاعات را تغییر دهد، حتی اگر در `backend/activity/routes.py` نیامده باشد، با یک خط عمومی ثبت می‌شود؛ برای شرح فارسی بهتر یک خط به همان فایل اضافه کنید.

## به‌روزرسانی پنل از داخل تنظیمات

تنظیمات ← **به‌روزرسانی پنل** (فقط مالک): نسخهٔ جدید را در GitHub بررسی می‌کند، تغییراتش را نشان می‌دهد و با دکمهٔ «به‌روزرسانی» همان کاری را می‌کند که تا حالا دستی می‌کردید: `git pull` و `docker compose up -d --build`. پیشرفت را زنده می‌بینید، پنل وقتی سرویس‌ها دوباره بالا می‌آیند ۱۰ تا ۳۰ ثانیه قطع می‌شود و بعدش خودکار برمی‌گردد. اگر نسخهٔ جدید آماده باشد، کنار «نسخهٔ پنل» در منوی کناری یک نقطهٔ نارنجی می‌افتد.

**راه‌اندازی (فقط یک بار):** این قابلیت سرویس تازهٔ `control` را لازم دارد. یک بار روی سرور، در پوشهٔ پروژه:

```bash
git pull && docker compose up -d --build
```

از آن به بعد همهٔ به‌روزرسانی‌ها از همان صفحه است. تا وقتی `control` بالا نباشد، صفحه همین دستور را نشان می‌دهد و بقیهٔ پنل بی‌مشکل کار می‌کند.

**شرط‌ها:**

- پوشهٔ پروژه روی سرور باید یک clone گیت روی یک **شاخه** باشد (مثل `main`) و `origin` بدون رمز در دسترس باشد: آدرس `https://` یک مخزن عمومی (همین حالت پیش‌فرض) یا مخزنی که رمزش داخل آدرس remote است. کلید SSH سرور داخل کانتینر نیست، برای همین اگر clone با آدرس SSH گیت‌هاب (`git@github.com:…`) ساخته شده، پنل همان مخزن را خودکار از راه https می‌گیرد (مخزن باید عمومی باشد).
- اگر سرور مستقیم به GitHub نمی‌رسد، `GIT_PROXY` را در `.env` بگذارید (مثل `BUILD_PROXY`؛ اگر خالی باشد همان `BUILD_PROXY` استفاده می‌شود).
- `git pull` فقط `--ff-only` است: اگر روی سرور فایل ردیابی‌شده‌ای را دستی عوض کرده باشید و با تغییر جدید تداخل داشته باشد، به‌روزرسانی با پیام خطا متوقف می‌شود و چیزی خراب نمی‌شود. صفحه قبلش هشدار می‌دهد که فایل تغییرکرده هست.
- در حین پشتیبان‌گیری یا بازگردانی دکمه کار نمی‌کند (۴۰۹)؛ بعد از پایانش دوباره بزنید. قبل از هر به‌روزرسانی یک پشتیبان بگیرید؛ مهاجرت دیتابیس خودکار اجرا می‌شود و برگشتن از آن فقط با بازگردانی پشتیبان است.

**امنیت:** دسترسی به `docker.sock` یعنی دسترسی root به سرور. برای همین فقط سرویس کوچک `control` (`control/control.py`، کمی بیش از ۴۰۰ خط) آن را دارد؛ روی هیچ پورتی منتشر نمی‌شود، فقط backend با یک توکن تصادفی (volume مشترک `control-token`، فقط‌خواندنی برای backend) می‌تواند صدایش کند، و backend هم این بخش‌ها را فقط برای نقش **مالک** باز می‌کند. هیچ نقش یا کاربری، حتی «سفارشی»، نمی‌تواند این دسترسی را بگیرد. مالک بودن یعنی کنترل کامل سرور؛ رمز حساب مالک را قوی نگه دارید و دسترسی پنل را (بخش «محدودیت IP» در `nginx/default.conf`) ببندید.

**چطور کار می‌کند:** گرفتن تغییرات و خود به‌روزرسانی داخل کانتینرهای کمکی کوتاه‌عمر اجرا می‌شوند (همین ایمیج `control`): با شبکهٔ میزبان (پروکسی روی `127.0.0.1` سرور کار می‌کند)، با همان کاربری که صاحب پوشهٔ پروژه است (فایل root-owned در `.git` نمی‌ماند) و با پوشهٔ پروژه روی همان مسیر واقعی (تا docker compose مسیرهای نسبی را درست پیدا کند). کار به‌روزرسانی عضو پروژهٔ compose نیست، پس با دوباره‌ساخته‌شدن خود سرویس‌ها نمی‌میرد؛ لاگش تا به‌روزرسانی بعدی می‌ماند (`docker logs asandesk-update-job`).

## لاگ داکر

تنظیمات ← **لاگ داکر** (فقط مالک): لاگ هر سرویس همین پروژه (backend، frontend، nginx، دیتابیس، scheduler، agent، control و آخرین کار به‌روزرسانی) با جست‌وجو، فیلتر «خطا و هشدار»، نمایش زنده (هر ۳ ثانیه)، کپی و دانلود. معادل `docker compose logs --tail N <service>` است. فقط کانتینرهای همین پروژه فهرست می‌شوند. لاگ‌ها می‌توانند آدرس‌ها و شناسه‌های داخلی را نشان بدهند؛ برای همین فقط مالک می‌بیند.

## خطای «password authentication failed for user»

اگر پوشهٔ پروژه را پاک کردید و دوباره نصب کردید، با این خطا روبه‌رو می‌شوید:

```
FATAL:  password authentication failed for user "asandesk"
```

دلیلش این است که `POSTGRES_PASSWORD` فقط وقتی اعمال می‌شود که volume دیتابیس **برای اولین بار** ساخته شود. پاک کردن پوشه volume را پاک نمی‌کند (`asandesk-dashboard_pgdata`)، پس دیتابیس هنوز رمز قدیمی را دارد و `.env` تازه رمز دیگری.

**راه اول، داده‌ها بمانند (رمز قدیمی لازم نیست):**

```bash
sh scripts/sync-db-password.sh
```

این اسکریپت از داخل کانتینر دیتابیس وصل می‌شود (اتصال محلی نیاز به رمز ندارد)، رمز کاربر دیتابیس را با `.env` یکی می‌کند و بقیهٔ سرویس‌ها را بالا می‌آورد.

**راه دوم، دیتابیس خالی و از نو (همهٔ داده‌ها پاک می‌شود، از جمله حساب مالک و بازخوردها):**

```bash
docker compose down
docker volume rm asandesk-dashboard_pgdata
docker compose up -d --build
```

بعدش دوباره کد راه‌اندازی را بگیرید و حساب مالک را بسازید. فایل‌های نسخه‌ها و پشتیبان‌ها در volumeهای جدا هستند و با این دستور پاک نمی‌شوند. دستور `docker compose down -v` را نزنید، چون همهٔ volumeها را پاک می‌کند.

## به‌روزرسانی خودکار کلاینت

بعد از هر انتشار این دو فایل بازنویسی می‌شوند:

- `/releases/latest.json`: آخرین نسخه پایدار
- `/releases/latest-beta.json`: جدیدترین نسخه بتا یا پایدار

```json
{
  "version": "2.5.0", "channel": "stable", "date": "2026-10-01",
  "mandatory": false, "rollout": 100, "notes": ["..."],
  "assets": { "windows": { "url": ".../api/releases/2.5.0/download/windows/AsanDesk-2.5.0-install.exe", "size": 123, "sha256": "..." } }
}
```

در کلاینت، `ORG_UPDATE_URL` در `src/asandesk.rs` به همین فایل اشاره می‌کند (`https://api.asandesk.ir/releases/latest.json`) و `do_check_software_update` آن را می‌خواند. آدرس دانلود هر دارایی به نام کامل فایل نصب ختم می‌شود، چون کلاینت فایل را با همان نام ذخیره و اجرا می‌کند.

**شمار نصب‌ها:** وقتی فایل نصب روی CDN است دانلودش از پنل نمی‌گذرد و پنل نمی‌تواند آن را بشمارد. «نصب تازه · ۳۰ روز اخیر» پس هر دستگاهی است که اولین درخواستش (`first_seen`) در ۳۰ روز اخیر به API رسیده؛ یعنی نصب‌شده و باز شده، نه فقط دانلودشده. کنار هر نسخهٔ تاریخچه هم شمار دستگاه‌های فعال ۳۰ روز اخیر روی همان نسخه آمده. شمارندهٔ دانلود از خود پنل (`downloads_30d` و `Release.downloads`) فقط برای فایل‌هایی است که از `/api/releases/<version>/download/…` پنل داده شوند.

لینک‌های دانلود از آدرسی ساخته می‌شوند که پنل هنگام انتشار نسخه با آن باز شده بود. اگر پنل را با IP باز می‌کنید ولی کلاینت‌ها باید از دامنه دانلود کنند، `PUBLIC_BASE_URL` را تنظیم کنید.

### انتشار از روی لینک و فایل `update.json`

نسخه‌های جدید اپلیکیشن (۱٫۴٫۹٫۱ به بعد) فقط `https://update.asandesk.ir/update.json` را می‌خوانند. در تب «نسخه‌ها» فرم انتشار این‌ها را می‌گیرد:

- **شمارهٔ نسخه** سه یا چهاربخشی (مثل `1.4.9.4`)، شمارهٔ بیلد، توضیحات تغییرات، پیام به کاربران، حالت تعمیر، فعال بودن و به‌روزرسانی اجباری.
- **لینک دانلود هر پلتفرم** به‌جای بارگذاری فایل. داشبورد فایل را خودش از لینک دانلود می‌کند (تا حداکثر `RELEASE_MAX_FILE_SIZE`)، SHA-256 و حجمش را حساب می‌کند و کنار نسخه نگه می‌دارد. لینک باید `https` و روی `asandesk.ir` یا زیردامنه‌هایش باشد (همان قاعده‌ای که اپلیکیشن دارد، و جلوی فرستادن درخواست از داشبورد به جاهای دیگر را هم می‌گیرد). اگر هر لینک خراب بود، چیزی ثبت نمی‌شود.

بعد از انتشار، کارت «فایل update.json» پایین صفحه فایل همان نسخه را با قالب اپلیکیشن می‌سازد: پیش‌نمایش، **دانلود**، کپی، و ویرایش بیلد، پیام، تعمیر، فعال و اجباری (ذخیره می‌شود و فایل دوباره ساخته می‌شود). همین دانلود در ردیف هر نسخهٔ تاریخچه هم هست. نمونه:

```json
{
  "app": "AsanDesk", "version": "1.4.9.4", "build": 1494, "force_update": false,
  "download_url": "https://update.asandesk.ir/releases/1.4.9.4/AsanDesk-1.4.9.4-x86_64-install.exe",
  "downloads": { "windows": "…exe", "linux": "https://update.asandesk.ir/releases/1.4.9.4/asandesk-1.4.9.4.deb" },
  "release_notes": "خط اول\nخط دوم", "message": "", "notice_title": "", "maintenance": false, "enabled": true,
  "support": { "bale_url": "https://ble.ir/join/AqZGNkLToJ", "bale_id": "" }
}
```

- `downloads.<os>` همان لینکی است که شما دادید؛ برای فایلی که بارگذاری کرده باشید لینک دانلود خود داشبورد می‌آید (اگر روی دامنهٔ آسان‌دسک با https نباشد، زیر فرم هشدار می‌دهد که اپلیکیشن آن را نمی‌پذیرد).
- `notice_title` (فیلد «عنوان چیپ نارنجی» در فرم انتشار و ویرایش): متنی که روی خود چیپ نارنجی حالت تعمیر در اپلیکیشن می‌نشیند؛ خالی یعنی «سرویس در حال تعمیر است». «پیام به کاربران» بعد از کلیک روی چیپ نشان داده می‌شود. نسخه‌های اپ قدیمی‌تر از 1.4.9.8 این فیلد را نادیده می‌گیرند.
- `download_url` فقط وقتی ویندوز دارید و همیشه exe ویندوز است (نسخه‌های ۱٫۴٫۹٫۱ و ۱٫۴٫۹٫۲ فقط همین را می‌شناسند).
- فایل را خودتان روی CDN بگذارید. اول فایل‌های نصب و آخر `update.json`.
- **حذف نسخه:** اگر نسخه‌ای را اشتباه منتشر کردید، در «تاریخچه انتشار» دکمهٔ سطل زباله کنار آن را بزنید (فقط با دسترسی «ویرایش» بخش نسخه‌ها). رکورد، فایل‌های نصبی که داشبورد خودش نگه می‌داشت و شمارندهٔ دانلودها پاک می‌شود و `latest.json` دوباره ساخته می‌شود. فایلی که خودتان روی CDN گذاشته‌اید و `update.json`ی که بارگذاری کرده‌اید را باید خودتان جایگزین یا پاک کنید.
- `support.bale_url` کانال آسان‌دسک در بله است. اپلیکیشن در پنجرهٔ «ارسال بازخورد»، برگهٔ «ارتباط با ما»، همین لینک (و `bale_id` اگر پر باشد) را نشان می‌دهد. در فرم انتشار و در کارت update.json قابل ویرایش است، پیش‌فرضش `https://ble.ir/join/AqZGNkLToJ` است و فقط `https` روی `ble.ir` پذیرفته می‌شود. اگر فیلد نباشد یا نامعتبر باشد، اپلیکیشن لینک داخل خودش را نشان می‌دهد.

## صفحه‌های خطا

خطاهای خود nginx (مثلاً ۴۰۴ برای هر مسیر غیرمجاز روی `api.asandesk.ir`، یا ۵۰۲ وقتی یکی از سرویس‌ها بالا نیست) صفحهٔ خطای برندشده می‌گیرند: ۴۰۴، ۴۰۳، ۵۰۰ و ۵۰۳ (برای ۵۰۲ و ۵۰۳ و ۵۰۴). پاسخ خطای خود backend (JSON) دست‌نخورده به کلاینت می‌رسد، پس اپلیکیشن چیزی متفاوت نمی‌بیند. صفحه‌های ۴۰۴ و ۵۰۰ خود پنل را Next.js می‌دهد (`frontend/src/app/not-found.tsx` و `error.tsx`) با همان طرح.

- صفحه‌ها استاتیک‌اند (`nginx/errors/api` و `nginx/errors/panel`) و با خرابی backend هم نمایش داده می‌شوند. متن و طرح در `scripts/gen-error-pages.py` است؛ بعد از ویرایش `python3 scripts/gen-error-pages.py` را اجرا کنید و خروجی را کامیت کنید.
- هر صفحه یک **شناسهٔ پیگیری** دارد (مثل `AD-7F3K-92QX`) با دکمهٔ کپی. این ۸ نویسهٔ اول `$request_id` است و در لاگ دسترسی nginx به‌صورت `rid=…` (کامل) هست: `docker compose logs nginx | grep rid=7f3k92qx`.
- نسخهٔ nginx در پاسخ‌ها نمایش داده نمی‌شود (`server_tokens off`).

## کلاینت‌ها و بازخوردها

### اتصال کلاینت‌ها به پنل

اپلیکیشن آسان‌دسک (fork از RustDesk) با «API سرور» RustDesk حرف می‌زند و پنل همان API را پیاده کرده است. در کلاینت `ORG_API_SERVER = https://api.asandesk.ir` (در `src/asandesk.rs`) قفل شده است.

#### دو زیردامنه (پنهان ماندن پنل از کاربران)

کلاینت‌های عمومی فقط `api.asandesk.ir` را می‌شناسند. `nginx/default.conf` روی این نام فقط مسیرهای جدول زیر، بازخورد اپ و آپدیت (`latest.json` و دانلود) را جواب می‌دهد و بقیه (پنل، `/admin`، API پنل) ۴۰۴ می‌شود. پنل مالک روی `panel.asandesk.ir` (یا IP سرور) است؛ برای امنیت بیشتر بلاک `allow/deny` همان فایل را با IP تیم پر کنید. هر دو زیردامنه به همین سرور اشاره می‌کنند. کلاینت فقط HTTPS معتبر قبول می‌کند، پس جلوی `api.asandesk.ir` گواهی TLS لازم است (مثلاً certbot روی nginx میزبان که به `HTTP_PORT` پروکسی کند).

#### حریم خصوصی

کاربر موقع نصب مطلع می‌شود که اطلاعات دستگاه و اتصال‌ها برای پشتیبانی فرستاده می‌شود و می‌تواند از تنظیمات خاموشش کند (کلید «ارسال اطلاعات برای پشتیبانی»؛ خاموش = کلاینت هیچ گزارشی نمی‌فرستد). ثبت IP کلید جداگانه‌ای در بخش امنیت دارد: کلاینت در sysinfo پرچم `loc` را می‌فرستد و پنل فقط وقتی روشن است IP را ذخیره می‌کند؛ خاموش‌شدنش IP ذخیره‌شده را هم پاک می‌کند (`Client.share_location`).

مسیرهایی که کلاینت صدا می‌زند (کد: `backend/clients/client_api.py`):

| مسیر | کاربرد |
|---|---|
| `POST /api/heartbeat` | هر ۱۵ ثانیه (هنگام اتصال هر ۳ ثانیه): آنلاین بودن و فهرست اتصال‌های باز. پاسخ همیشه `blocked: true/false` دارد |
| `POST /api/sysinfo` | سیستم‌عامل، نسخه برنامه، نام دستگاه، سخت‌افزار |
| `POST /api/audit/conn` | شروع، احراز هویت و پایان هر اتصال ریموت ← مدت اتصال، «آخرین نشست‌ها» و «درخواست‌های اتصال» (در close می‌تواند `result: failed \| cancelled` هم بیاید) |
| `POST /api/login`، `/api/currentUser`، `/api/logout` | ورود کاربر به حساب از داخل اپلیکیشن |

- **شناسایی دستگاه:** شناسه (ID) و uuid دستگاه. uuid در اولین تماس ثبت می‌شود و تماس بعدی با همان شناسه ولی uuid دیگر رد می‌شود. اگر برنامه روی دستگاه دیگری با همان شناسه نصب شد، در `/admin/clients/client/` اکشن «بازنشانی کلید دستگاه» را بزنید.
- **حساب‌های کاربری اپلیکیشن** (ایمیل/رمز، طرح رایگان یا حرفه‌ای) را مالک در `/admin/clients/account/` می‌سازد. ثبت‌نام از داخل اپلیکیشن هنوز وجود ندارد. دفترچه آدرس (address book) و گروه‌ها پشتیبانی نمی‌شوند.
- **مسدودسازی:** با دکمهٔ «مسدودسازی» (پس از تأیید) در heartbeat بعدی دستگاه `blocked: true` می‌گیرد. اپلیکیشن (از 1.5.0) آن لحظه سرور شناسه، رله، کلید و آدرس API را از روی خودش برمی‌دارد (به نامی که هرگز resolve نمی‌شود اشاره می‌دهد، نه به سرور عمومی RustDesk)، اتصال‌های باز قطع می‌شود، از حساب خارج می‌شود و بنر «مسدود شده» نشان می‌دهد. وضعیت بعد از راه‌اندازی دوباره هم می‌ماند. دستگاه مسدود فقط هر ۱۵ ثانیه از `api.asandesk.ir` می‌پرسد «مسدودیتم برداشته شد؟» (با `revoked: true`)، و تا پاسخ صریح `blocked: false` نیاید چیزی را برنمی‌گرداند؛ با «رفع مسدودیت» اطلاعات سرور برمی‌گردد. `Client.revoked_at` اولین باری است که دستگاه گزارش داده اطلاعات را پاک کرده؛ پنل کلاینت «در انتظار ارتباط دستگاه» یا «پاک شد» را نشان می‌دهد. **محدودیت:** دستگاهی که خاموش است، یا «ارسال اطلاعات برای پشتیبانی» را خاموش کرده، پیام را نمی‌گیرد (آن گزینه heartbeat را هم خاموش می‌کند). نسخه‌های اپ قدیمی‌تر از 1.5.0 فیلد `blocked` را نمی‌شناسند و فقط اتصال‌های ورودی‌شان قطع می‌شود. جلوی اتصال خروجی با سرور hbbs خودتان را همچنان فقط خود سرور می‌تواند بگیرد.
- **خروج اجباری:** توکن ورود دستگاه باطل می‌شود و اپلیکیشن در بررسی بعدی حساب از حساب خارج می‌شود.
- **بدون داده:** پهنای باند مصرفی هر کلاینت و آمار تبلیغات (کلاینت گزارش نمی‌دهد یا هنوز پیاده نشده)، موقعیت جغرافیایی (پنل پایگاه GeoIP ندارد و فقط IP نمایش داده می‌شود، آن هم با اجازهٔ کاربر) و رضایت کاربران (نظرسنجی هنوز پیاده نشده).

### بازخورد از داخل اپلیکیشن

دکمهٔ «ارسال بازخورد» در اپلیکیشن (منوی ☰، صفحهٔ اصلی و پنل جلسه) متن کاربر، لاگ برنامه و تا ۳ تصویر را می‌فرستد. هر بازخورد در تب «بازخوردها» یک ردیف می‌شود: دسته (مشکل/پیشنهاد/سایر)، متن، راه تماس، اطلاعات پیوست (نسخه، سیستم‌عامل، صفحه، زبان)، دکمهٔ **دانلود لاگ** و پیش‌نمایش تصویرها (با کلیک در اندازهٔ اصلی باز می‌شوند).

```text
POST /api/client/feedback   {"id", "uuid", "category": bug|idea|other, "message", "contact"?, "version", "os", "os_version",
                             "screen", "lang", "theme", "log_attached", "log": gzip+base64, "log_files": [...],
                             "images"?: [{"name", "mime", "data": base64}]  // حداکثر ۳}
                            →  201 {"ok": true, "id": "T-1042", "images": 2}
```

- بدنه تا ۸ مگابایت است (روی `api.asandesk.ir` همان `client_max_body_size 8m`؛ بعد از به‌روزرسانی nginx را دوباره بالا بیاورید). لاگ با سقف `FEEDBACK_MAX_LOG_MB` باز می‌شود تا فایل فشردهٔ مخرب حافظه را پر نکند، و بازشده کنار دیتابیس در volume `releases/feedback-logs/` نگه‌داری می‌شود (از بیرون در دسترس نیست؛ فقط با دسترسی بخش بازخوردها از پنل دانلود می‌شود). با حذف بازخورد، فایل لاگ هم پاک می‌شود.
- تصویرها: حداکثر ۳ عدد و هرکدام تا `FEEDBACK_MAX_IMAGE_MB` (پیش‌فرض ۲ مگابایت). نوع تصویر از روی محتوا تشخیص داده می‌شود (PNG/JPEG/GIF/WebP؛ هر چیز دیگر ۴۰۰)، نه از نامی که کلاینت می‌گوید. کنار لاگ در `releases/feedback-images/` ذخیره و فقط پشت ورود به پنل (`/api/tickets/<id>/images/<n>`) نمایش داده می‌شود؛ با حذف بازخورد، فایل‌ها هم پاک می‌شوند. این نسخه یک migration جدید دارد (`clients/0004_ticketimage`) که با `docker compose up -d --build` خودکار اجرا می‌شود.
- دستگاهی که تا حالا heartbeat نفرستاده همین‌جا ثبت می‌شود (اگر «ارسال اطلاعات برای پشتیبانی» را خاموش کرده باشد). دستگاه مسدود یا با uuid نادرست بازخورد نمی‌فرستد؛ هر دستگاه در ساعت `CLIENT_FEEDBACK_PER_HOUR` بازخورد می‌تواند بفرستد.
- بازخورد پاسخ ندارد: پنل راهی برای نوشتن به کاربر ندارد و اپلیکیشن هم فهرست یا پاسخی نشان نمی‌دهد. وضعیت فقط «جدید» یا «بررسی‌شده» است (کد `T-xxxx` فقط شمارهٔ پیگیری داخلی است). اگر کاربر در «شماره تماس» چیزی نوشته باشد، بالای بازخورد دیده می‌شود (با دکمهٔ تماس و کپی) و در فهرست فیلتر «نیازمند تماس» هست؛ بقیه فقط خوانده می‌شوند.
- لاگ‌ها اطلاعات شخصی (شناسهٔ دستگاه‌ها، آدرس شبکه) دارند؛ فقط به نقش‌هایی دسترسی بدهید که لازم دارند.

مسیرهای قدیمی تیکت (`/api/client/tickets/new|list|<id>/reply`) و «ارسال پیام» از تب کلاینت‌ها در 1.7.0 حذف شدند؛ اپلیکیشن فقط `/api/client/feedback` را صدا می‌زند.

## محدودیت‌ها و حفاظت در برابر سوءاستفاده

نقطه‌های عمومی (`api.asandesk.ir`) را هر کسی می‌تواند صدا بزند، پس این لایه‌ها هست (جزئیات و چیزهایی که باید روی سرور شناسه و رله بکنید: `docs/SERVER-HARDENING.md`):

* **آدرس واقعی کاربر پشت CDN.** `nginx/cdn-ips.conf` شبکه‌های CDN را فهرست می‌کند (آروان‌کلود، از `https://www.arvancloud.ir/en/ips.txt`)؛ فقط درخواستی که از آن شبکه‌ها برسد آدرس کاربر را از `X-Forwarded-For` می‌گیرد، و درخواست مستقیم به سرور هر سرآیندی بفرستد آدرس خودش می‌ماند. به‌روزرسانی فهرست: `sh scripts/update-cdn-ips.sh && docker compose up -d nginx`. اگر CDN ندارید فایل را خالی بگذارید.
* **محدودیت نرخ در nginx** (به‌ازای هر آدرس): heartbeat و sysinfo ۶۰ در ثانیه (با صف ۱۰۰)، بازخورد ۶ در دقیقه، ورود ۱۵ در دقیقه، ورود پنل با بدنهٔ حداکثر ۱۶ کیلوبایت. جواب بیش از سقف `429` است. عددها بالای `nginx/default.conf` هستند؛ اگر دفتری با صدها دستگاه پشت یک IP دارید `asan_device` را بالا ببرید.
* **سقف در Django** (با `.env` عوض می‌شود): `CLIENT_NEW_DEVICES_PER_IP_HOUR` (دستگاه تازه در ساعت از یک آدرس، پیش‌فرض ۱۰۰)، `CLIENT_FEEDBACK_PER_IP_HOUR` (۳۰)، `FEEDBACK_MAX_TOTAL_MB` (۲۰۴۸؛ بعد از پر شدن فضای لاگ و تصویر، بازخورد فقط با متن ذخیره می‌شود و پاسخ `attachments_dropped` دارد). شمارنده‌ها فقط در حافظهٔ هر پردازه و بدون ذخیرهٔ IP هستند.
* **ورود پنل** به‌ازای آدرسی که nginx دیده محدود می‌شود، نه سرآیندی که کاربر می‌نویسد (`accounts/throttles.py`).
* **مسدودسازی ماشین.** حکم «مسدود» برای همهٔ شناسه‌هایی است که `uuid` (شناسهٔ ماشین) یکسان دارند؛ نصب دوباره شناسهٔ تازه می‌دهد ولی مسدود می‌ماند. رفع مسدودیت هم همهٔ آن‌ها را آزاد می‌کند. (ماشین‌های مجازی کپی‌شده از یک تصویر ممکن است `uuid` یکسان داشته باشند.)
* **سرآیندهای امنیتی** (CSP، `nosniff`، `Referrer-Policy`، HSTS فقط وقتی کاربر با https آمده) را nginx می‌دهد. وقتی پنل را همیشه با https باز می‌کنید `SECURE_COOKIES=1` را در `.env` بگذارید.
* **ظرفیت.** gunicorn با `gthread`، تعداد پردازه و نخ از `WEB_CONCURRENCY` (۴) و `GUNICORN_THREADS` (۴).
* **امضای update.json.** داشبورد برای `update.json` یک امضای Ed25519 جداگانه می‌سازد (`update.json.sig`؛ کلید فقط در volume رازها می‌ماند و `python manage.py update_signing_key` کلید عمومی را نشان می‌دهد). کلید عمومی را در `src/asandesk.rs` (`UPDATE_SIGNING_KEYS`) بگذارید و برنامه را دوباره بسازید؛ از آن نسخه به بعد برنامه update.json بدون امضای درست را نادیده می‌گیرد. هر بار update.json را روی CDN می‌گذارید `update.json.sig` را هم بگذارید. **از فایل `secrets/update_signing_key` یک نسخهٔ پشتیبان آفلاین نگه دارید** (`python manage.py update_signing_key --private`)؛ اگر کلید گم شود برنامه‌های نصب‌شده دیگر به‌روزرسانی را قبول نمی‌کنند.

## مانیتورینگ و هشدارها

قوانین هشدار در `backend/monitoring/alerts.py` تعریف شده‌اند:

| قانون | سطح |
|---|---|
| میانگین CPU بالای ۸۰٪ در ۱۰ دقیقه | بحرانی |
| RAM بالای ۹۰٪ | هشدار |
| دیسک بالای ۸۵٪ | هشدار (بالای ۹۵٪ بحرانی) |
| بیش از ۲ دقیقه بدون گزارش از سرور | بحرانی |

هشدارها با برگشت وضعیت به حالت عادی خودبه‌خود بسته می‌شوند. نمونه‌های قدیمی‌تر از `METRICS_RETENTION_DAYS` (پیش‌فرض ۹۰ روز) حذف می‌شوند.

«نشست‌های موفق»، «درخواست‌های اتصال» (امروز و بازهٔ انتخاب‌شده) و «توزیع نسخه‌ها بین کاربران» از گزارش کلاینت‌ها پر می‌شوند (بخش «کلاینت‌ها و بازخوردها»). این مورد هنوز «بدون داده» نمایش داده می‌شود:
- توزیع پلتفرم/منطقه کانکشن‌های فعال

**درخواست‌های اتصال** هر اتصالی است که به یک دستگاه کنترل‌شونده رسیده و آن دستگاه در `audit/conn` گزارشش کرده. موفق = احراز هویت شد؛ «در انتظار» = کمتر از ۲ دقیقه پیش شروع شده و هنوز باز است؛ بقیه بی‌نتیجه‌اند، و «نرخ اتصال ناموفق» همین‌ها را از درخواست‌های تمام‌شده حساب می‌کند. دو محدودیت:
- درخواستی که هرگز به دستگاه نرسد (مثلاً خطای شبکه یا سرور شناسه/رله) در این آمار نیست. دیدنش فقط از لاگ خود hbbs/hbbr ممکن است.
- **«ناموفق» و «لغو شده» تا وقتی اپ علت را نفرستد از هم جدا نمی‌شوند** و با هم «ناموفق یا لغو شده» نشان داده می‌شوند. اپ در گزارش پایان اتصال (`action: "close"`) می‌تواند `"result": "failed"` یا `"result": "cancelled"` را اضافه کند (`ConnSession.result`)؛ مقدار دیگر نادیده گرفته می‌شود و اپ‌های قدیمی بدون آن همچنان کار می‌کنند. با رسیدن اولین علت، کارت دو عدد جدا نشان می‌دهد.

«کانکشن‌های همزمان» فعلاً تعداد اتصال‌های TCP برقرار روی سرور است. وقتی hbbs/hbbr روی سرور نصب شد، با `AGENT_PORTS=21116,21117` فقط اتصال‌های آسان‌دسک شمرده می‌شوند.

### افزودن سرور دیگر (مثلاً رله‌ها)

1. در `/admin/monitoring/server/add/` سرور را بسازید. توکن agent یک بار نمایش داده می‌شود.
2. روی آن سرور فقط agent را اجرا کنید:

```bash
docker build -t asandesk-agent ./agent
docker run -d --restart unless-stopped --pid host \
  -v /:/hostfs:ro -v /sys:/hostsys:ro \
  -e AGENT_URL=https://panel.example.com/api/agent/ingest \
  -e AGENT_TOKEN=<token> -e AGENT_DISK_PATH=/hostfs -e AGENT_SYS=/hostsys \
  asandesk-agent
```

> روی Docker Desktop (ویندوز/مک)، «میزبان» در واقع ماشین مجازی لینوکسی داکر است و منابع همان نمایش داده می‌شود. روی سرور لینوکسی منابع واقعی خود سرور نمایش داده می‌شود.

## تنظیمات (کاربران، پشتیبان‌گیری) و سرورهای HA

سرویس `scheduler` (همان ایمیج backend) باید بالا باشد؛ پشتیبان‌گیری خودکار، صف بازگردانی و بررسی سلامت سرورهای HA را اجرا می‌کند. اگر پایین باشد، پنل هشدار «سرویس زمان‌بند فعال نیست» نشان می‌دهد.

**کاربران و دسترسی‌ها.** نقش‌ها: مالک (قفل، همه‌چیز)، مدیر، ناظر و سفارشی. در نقش سفارشی برای هر بخش (سرور، نسخه‌ها، کلاینت‌ها، بازخوردها، تبلیغات، کاربران، پشتیبان‌گیری، HA) یکی از «بدون دسترسی / مشاهده / ویرایش» انتخاب می‌شود. دسترسی در backend بررسی می‌شود و کسی نمی‌تواند بیش از دسترسی خودش به دیگری بدهد.

**پشتیبان‌گیری.**
- هر روز در ساعت تنظیم‌شده یک فایل `.adbk` ساخته می‌شود (پیش‌فرض ۰۳:۰۰ و نگه‌داری ۱۴ روز؛ ۱ تا ۹۰ قابل تغییر). فقط پشتیبان‌های *خودکار* قدیمی حذف می‌شوند؛ دستی و ایمنی ماندگارند.
- محتوا: همهٔ جدول‌های دیتابیس (با سریالایزر Django، مستقل از نسخهٔ Postgres) و در صورت انتخاب فایل‌های نصب نسخه‌ها.
- بازگردانی همه‌چیز را با پشتیبان جایگزین می‌کند، همهٔ نشست‌ها را می‌بندد و به‌صورت پیش‌فرض اول یک پشتیبان ایمنی از وضعیت فعلی می‌گیرد.
- فایل‌ها روی volume `backups` (`/data/backups`) هستند. این volume روی همان سرور است؛ برای محافظت در برابر خرابی سرور، فایل‌ها را دانلود یا به جای دیگری کپی کنید.

**سرورهای HA** (منوی اصلی ← «سرورهای HA»). برای هر سرور شناسه/رله پورت‌های 21115 تا 21119 (TCP) و 21116 UDP واقعاً آزمایش می‌شوند؛ سرور فعال سالم‌ترین سرور با کمترین اولویت است. پنل فقط وضعیت و «سرور فعال» را ثبت می‌کند؛ جابه‌جایی واقعی ترافیک با DNS یا IP شناور (keepalived) روی خود سرورها/DNS انجام می‌شود. برای سنجش یکسان بودن کلید، agent را با `AGENT_KEY_FILE` (مسیر `id_ed25519.pub` سرور شناسه) اجرا کنید؛ دستور آمادهٔ نصب در دیالوگ «افزودن سرور» هست.
